# EscrowScope v0.4 Implementation Plan

> **Build rule (overrides everything):** Vihaan types every line of app code
> and test code. Claude explains concepts, gives exact terminal commands,
> and reviews. That is why this plan has contracts and expected outputs
> instead of pasted code. Spec: docs/specs/2026-07-30-v0.4-statement-extraction-design.md

**Goal:** Paste an escrow statement, click Extract, fields fill in, human
verifies, existing engine renders the verdict. Mock extractor, live on
GitHub Pages.

**Architecture:** One new module (`extract.js`) with one function, one new
data file (`sample-statement.txt`), wiring added to `index.html`, one new
test in `tests.js`. Engine untouched.

**Tech stack:** Plain JS (ES modules), no dependencies, Node for tests,
GitHub Pages for deploy.

## Global constraints

- Engine (`engine.js`) does not change in v0.4.
- Extracted numbers always land in the input fields for human review.
  They never trigger the verdict directly.
- Mock demo mode is stated honestly in the UI, never faked as real parsing.
- Every task ends with a commit. Push at the end of the session (Vihaan's
  call, repo is public).

### Task 1: sample-statement.txt (no code, ~20 min)

**Files:** Create `sample-statement.txt`

**Produces:** the text every later task parses and tests against.

Write a fake annual escrow analysis the way a servicer would word it.
Invent a servicer name (do not use a real company's name). It must contain,
somewhere in natural sentences or a simple table:

- Escrow account starting balance: $1,500.00
- Monthly escrow payment: $400.00
- County property tax, $1,800.00, paid May
- Homeowners insurance, $1,200.00, paid July
- County property tax, $1,800.00, paid November

Real statements also have noise: an account number, a greeting, a
"your new monthly payment" paragraph. Add some noise on purpose — the
sample should not be suspiciously clean, because the AI version will face
messy text.

      (Claude describes the standard sections; RESPA requires servicers to
      send this exact document, which is the app's whole audience)
- [ ] Step 2: Vihaan writes the letter in VS Code
- [ ] Step 3: Read it back: are all 5 numbers and 3 months present and
      unambiguous?
- [ ] Step 4: Commit
      Run: `git add sample-statement.txt && git commit -m "v0.4: sample statement for demo mode"`

### Task 2: extract.js with test-first (~45 min)

**Files:** Create `extract.js` · Modify `tests.js`

**Interfaces:**
- Produces: `extractStatement(text)` — takes one string. Returns
  `{ startingBalance: 1500, monthlyDeposit: 400, bills: [ { name, amount, month } × 3 ] }`
  when the text is the sample statement, `null` for anything it does not
  recognize. This exact shape is the contract for Task 3 and for the
  future AI extractor (v0.4.5).

Mock behavior, decided in the spec: the function looks for a distinctive
marker from the sample (for example the fake servicer's name) with
`.includes()`. Marker found → return the hardcoded object. Not found →
return `null`. That is the whole mock, and it is honest: the demo-mode
message in Task 3 tells the user this is what is happening.

- [ ] Step 1 (test first): Vihaan adds test #5 to `tests.js`: read
      `sample-statement.txt` with `readFileSync` (already used in
      check.js), call `extractStatement`, compare every field to the
      expected object. New concept: comparing objects/arrays needs
      field-by-field checks or `JSON.stringify` equality — `===` on two
      objects is false even when contents match. Claude explains why
      before he writes it.
- [ ] Step 2: Run `node tests.js` — expect FAIL (extract.js does not exist)
- [ ] Step 3: Vihaan writes `extract.js` (export, marker check, hardcoded
      return, null branch)
- [ ] Step 4: Run `node tests.js` — expect 5/5 PASS
- [ ] Step 5: Also test the null branch: call with "hello" → expect null
      (test #6, then 6/6 PASS)
- [ ] Step 6: Commit
      Run: `git add extract.js tests.js && git commit -m "v0.4: mock extractor with tests, 6/6 pass"`

### Task 3: wire the page (~1 hr)

**Files:** Modify `index.html`

**Interfaces:**
- Consumes: `extractStatement(text)` from Task 2,
  `sample-statement.txt` from Task 1.

New section above the existing fields: textarea (`id="statement"`),
"Load sample" button, "Extract numbers" button, and a message line
(`id="extract-msg"`). Behavior Vihaan implements:

- Load sample → `fetch("sample-statement.txt")` → put text in the
  textarea. New concepts: fetch + `.then()` / `await` in the browser
  (he has done fetch in Node in judge-multi.js — same idea).
- Extract → empty textarea → message "Paste a statement first (or click
  Load sample)." Otherwise call `extractStatement`. `null` → message
  "Demo mode: v0.4 only reads the built-in sample statement. Real
  statements come with the AI upgrade." Object → write values into the
  three existing inputs (bills as JSON via `JSON.stringify(bills, null, 2)`
  into the textarea) and message "Numbers extracted — check them, then
  hit Check the math."

Tooling note (Claude's job): `fetch` and ES modules do not work from a
double-clicked file. Test locally with a local server — VS Code's
Live Server extension, or `python3 -m http.server` in the repo folder,
then http://localhost:8000.
